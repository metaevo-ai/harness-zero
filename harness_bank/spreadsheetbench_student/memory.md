# Harness Memory

## Hard rules

1. Your FIRST `execute` call must be `cat /opt/ahd/harness/skills/spreadsheet-manipulation/SKILL.md`, before any exploration. The skill contains the workflow and the pitfall catalog for exactly these tasks; skipping it is the single most common cause of failure.
2. Output = the INPUT workbook edited in place and saved to the output path: `shutil.copy(INPUT, OUTPUT)` then modify with openpyxl, or `load_workbook(INPUT)` → modify → `wb.save(OUTPUT)`. NEVER create a fresh `Workbook()` or write results with `pandas.to_excel()` — both drop sheet names, extra sheets, and formulas, and the grader reports "worksheet not found" even when your values are right. After saving, reload and assert sheet names and header rows match the input exactly.
3. Pre-filled cells in the answer range and example/result sheets are the spec. Read them first, infer the rule from them, and never overwrite them — write only into blank cells. When instruction prose and examples conflict, the examples win. Before finishing, diff the saved output against the input inside the answer range: every pre-filled cell must be byte-identical unless the task explicitly requires changing it. A broken formula sitting in the answer area is usually the bug being complained about, not an example to copy.
4. Write literal computed values as the default. The grader recalculates both files with LibreOffice and compares values, so a formula can in principle score — but only if it is row-interpolated, mined from existing formula templates, and verified by a LibreOffice recalculation. The sandbox has NO LibreOffice and openpyxl writes no cached value, so you can never verify a formula there; an unverified formula is a gamble and computed literals are always safe. Treat "write a formula / SUMIFS / VBA / macro / should update automatically" as a specification of the logic, not of the deliverable format. Code, VBA, and explanations never go into workbook cells — they belong in your final summary text only.
5. Address cells by Excel coordinates with openpyxl (`ws["B3"]`, `column_index_from_string`), never by pandas positional indexing (its header handling shifts every row by one) and never `chr(64 + n)` or hand-computed column numbers (double-letter columns: AZ=52, BE=57 — verify by reading back the address string, e.g. `ws["BE9"]`). Ranges are closed intervals — include both endpoints. The answer_position boundary takes precedence over the instruction's start-cell wording.
6. Verify by assertion, not by printing. Before finishing, reload the saved output and assert every cell of answer_position against independent recomputation and the worked examples. Stop-and-fix signals: any string starting with `=` inside the answer range; `data_only=True` returning None; a conditionally-filled column where every row got the same value; a negative date difference or duration; zero hit rate on a lookup; text where numbers belong; your script's output contradicting your own hand enumeration of a few rows; grouping or totals that violate an explicit instruction constraint (group size, a quoted expected number such as "a total of 9,480"); a rule that writes zero net cells into the answer range. Numbers the instruction itself quotes are unit tests — your answer cells must reproduce them exactly, and a mismatch means your premise is wrong, not your arithmetic. Layout is part of the answer too: block structure, repeated headers, and blank masks from the examples must be replicated exactly — a blank cell that the examples leave blank is an answer.
7. The deliverable is always the manipulated workbook, even when the instruction reads like a forum question ("How can I ...", "Could you advise ..."). Instructions with imperative operations (delete / filter / insert / sort / fill these rows) demand the actually-modified workbook: an answer range flooded with repeated prose words ("Yes"/"No") or filled with advice text scores zero.
